01

How Storybook actually works

Storybook is not a component gallery. It is a build pipeline, a two-process runtime, and an event bus — and every visible feature is an addon plugged into that bus. Knowing those three layers is what lets us decide what to copy and what to reinvent.

The authoring format: CSF

A module with one default export describing the component and named exports describing each state. Six orthogonal concepts make up the entire data model.

Button.stories.ts
// meta — the default export
const meta = {
  title:      'Forms/Button',      // sidebar path
  component:  Button,
  args:       { label: 'Hi' },       // default prop values
  argTypes:   { variant: { control: 'select' } },
  parameters: { backgrounds: { default: 'dark' } },
  decorators: [withTheme],
  tags:       ['autodocs'],
};
export default meta;

// each named export is one story
export const Primary = { args: { variant: 'primary' } };
export const Loading = { args: { loading: true }, play: async (ctx) => { … } };
ConceptWhat it isMerge order
argsSerializable prop values. Change one, the component re-renders.global → component → story → URL
argTypesMetadata about each arg — type, description, default, which control widget. Auto-inferred, hand-overridable.same
parametersStatic, non-serializable config consumed by addons.same
decoratorsWrapper functions — theme provider, router, padding.outermost first
globalsApp-wide state set from the toolbar (theme, locale). Read by decorators.single scope
tagsStrings opting a story into behaviours — autodocs, !test.inherited, overridable

The build pipeline

  1. Indexer — globs every story file at build time and produces a flat index of {id, title, name, importPath, tags}. The sidebar tree is derived by splitting title on /.
  2. Docgen — a compiler plugin reads the component's prop types and JSDoc, emitting argTypes automatically. This is the magic that makes controls "just work."
  3. Builder — emits two bundles: the manager (the UI shell, framework-agnostic, ships prebuilt) and the preview (an iframe containing your framework runtime and your stories).

The runtime: two processes, one channel

The iframe is load-bearing, not cosmetic. Manager CSS cannot reach your component. A component that throws cannot take down the UI. And the preview URL — iframe.html?id=forms-button--primary&args=label:Hey — is independently addressable, which is exactly how the test runner, visual-regression snapshotting, and embedding all work.

What happens when you click a story

story lifecycle
click → manager emits setCurrentStory(id)
     → preview resolves the story, applies globals + parameters
     → composes decorators  (global ∘ component ∘ story)
     → renders with merged args
     → emits storyRendered  → manager unblocks its panels
     → if story.play exists: run it, instrument every interaction,
       stream each step to the Interactions panel

The short version

Storybook is great because of four things: controls generated from types (B1), stories that double as tests (E1, E2), documentation generated from the same source (D1), and a channel extensible enough that everything else is an addon (F2). The other thirty-two features are polish on top of those four.

03

The porting problems

Six things in the JavaScript design do not survive the trip into Rust. These are the real engineering risks — everything else is work, not risk.

P1

No runtime module discovery

JavaScript globs story files at runtime. Rust links everything at compile time, so stories have to be found some other way: a link-section registry via linkme, a build-script that generates a registry, or explicit hand-registration.

Settled in M0linkme does not compile on wasm32; inventory silently drops stories in dev builds. Build-script codegen is the registry. See section 05.

P2

No docgen, no reflection

There is no react-docgen for Rust. But we own the derive macro, which sees field names, types and doc comments statically — everything docgen extracts, except type-checked.

DecisionA #[derive(Controls)] macro emits the arg-type table. This is a genuine advantage over the original, not a workaround.

P3

Dynamic args into typed props

Storybook spreads a JSON object onto props. Serde cannot do the inverse here — props contain EventHandler and Element, neither of which is serializable.

DecisionGenerate an applier, not a deserializer: overlay dynamic values onto a typed base. Fields whose types aren't controllable simply get no widget — same as Storybook does for functions.

P4

Manager and preview isolation

Two Dioxus apps plus postMessage is the faithful port, but it means two wasm bundles and a build-orchestration story on day one.

DecisionDefine the Channel trait in the first commit. Run in-process through M2, then swap in the iframe implementation without rewriting a single addon.

P5

No testing library exists

Play functions need DOM querying and user-event simulation. Nothing like @testing-library exists for Dioxus.

DecisionA small crate over web-sys: get_by_role, get_by_text, get_by_test_id, plus user events with correct sequencing. Bounded but real — hence a late milestone.

P6

Multiplatform ambiguity

Dioxus targets web, desktop and mobile. Storybook is web-only. Trying to serve all three at once would dilute every decision.

DecisionWeb-first. The static build is both the shareable artifact and the substrate for screenshot testing. Desktop is nearly free later — the same code in a webview — but it is not the target.

The load-bearing assumption — corrected by M0

The plan assumed the project rested on Subsecond hot-patching Rust while preserving state. It does not. Subsecond is currently broken on wasm — but incremental rebuilds land in 1.5 seconds, which is fast enough on its own. The dependency is on rebuild speed, not on hot-patching. Section 05 has the measurements.

Worth noting on prior art: the storybook and storybook-derive crates exist, but they only bridge Rust WASM components into the JavaScript Storybook, and have roughly 150 downloads between them. Nobody has built a native one.

Where controls come from

The derive macro is the whole trick. It sees the field names, the types, and the doc comments — and unlike JavaScript docgen, what it produces is checked by the compiler.

src/components/button.rs
#[derive(Props, PartialEq, Clone, Controls)]
pub struct ButtonProps {
    /// Text shown inside the button.        → the docs description
    pub label: String,                     // → text control
    pub variant: ButtonVariant,            // → select, from derive(ControlEnum)
    #[control(range(min = 0.0, max = 4.0, step = 0.25))]
    pub scale: f32,                        // → range slider
    pub disabled: bool,                    // → toggle
    #[control(skip)]
    pub children: Element,
    pub onclick: EventHandler<MouseEvent>, // → auto-wired to Actions panel
}

M0 spike results

Three go/no-go questions, answered by running code rather than reading documentation. Toolchain: rustc 1.97.1, dx 0.7.10, dioxus 0.7.10, macOS aarch64.

GO The loop is fast enough and the macro works. One assumption was wrong, one option is dead, and one feature has to move earlier.
QuestionResult
S1Does the dev loop stay under 2s?Yes — but not via Subsecond, which is currently broken on wasm.Pass, revised
S2Can stories self-register on wasm?No. Both automatic mechanisms fail; codegen is the only reliable option.Option dead
S3Can a derive macro replace docgen?Yes, cleanly — 15/15 against real Dioxus types.Pass

S1 · The loop is fast, but not for the reason the plan assumed

dx serve --hot-patch does not build. The hot-patch path produces a fat archive that keeps every dependency object normal linking would garbage-collect — including std objects carrying wasm exception-handling opcodes — and dx's own module emitter parses without the exceptions feature enabled:

dx serve --platform web --hot-patch
ERROR Build failed: Failed to emit module: failed to parse import section
  2: exceptions proposal not enabled (at offset 0x33d24)

Isolated by A/B — without the flag the same project builds fine. panic = "abort" does not fix it (identical failure, identical offset), and exception-handling is not a default rustc target feature for wasm32, so this is a dx-versus-current-std incompatibility rather than a project misconfiguration. Worth filing upstream; not worth blocking on. Also worth knowing: --hot-patch defaults to false, and dx refuses to run when its version differs from the dioxus crate's.

None of which matters much, because the rebuild is fast on its own:

EditPath takenTime
rsx text node (markup)rsx hot reload, no rebuild0.36s
Rust logic outside rsxfull incremental rebuild1.52s
Story data in stories.rsfull incremental rebuild1.49s
Cold startfull build19–32s
The correction that matters

The plan said the project rested on Subsecond preserving state across a hot patch. It doesn't. It rests on the incremental rebuild being about 1.5 seconds — which it is, today, with hot-patching switched off entirely. Subsecond becomes an optimisation to adopt once it works on wasm, not a precondition to build on.

But a rebuild reloads the page, and a reload destroys every in-memory signal: selected story, edited args, scroll position. So feature A4 — deep-linkable URLs encoding story id and args — is not a sharing nicety. It is the mechanism that lets the dev loop survive a rebuild, and it moves from M2 into M1.

S2 · Both automatic registration mechanisms fail

The same three-crate fixture — four stories, checksum 131 — put through every mechanism, with the resulting wasm actually executed rather than merely compiled.

MechanismReleaseDebug (dx serve)Verdict
linkme 0.3.37won't compilewon't compileUnusable on wasm32
inventory 0.3.24passfail — 2 of 4Unreliable
build-script codegenpasspassAdopted

linkme rejects the target outright — distributed_slice is not implemented for this platform — while the identical code compiles for the host, so it is a platform gap rather than a usage error. inventory is the more dangerous result: registration is lost for any story in a codegen unit nothing else references. Bisecting codegen-units pins the mechanism exactly — 1 passes, 16 fails, 256 fails. Release builds use one unit and pass; dev builds use 256 and drop stories. It fails in the worst possible direction: stories vanish silently while you develop, and reappear in production.

A methodology note worth keeping

The first inventory run passed — a 916-byte module reporting exactly the right count. LTO had const-folded the entire registry into a literal, so the test proved nothing. Any future registry test has to defeat that: wrap the accessors in black_box and reconstruct each story id byte-by-byte out of linear memory, so that passing requires the data to genuinely exist at runtime.

S3 · The derive macro works, against real Dioxus types

Fifteen of fifteen tests pass against the actual Props derive, Element, and EventHandler<MouseEvent> — not stand-ins. The macro produced doc comments as descriptions, enums as selects with real variant names, Option<T> as optional with Null clearing it, Element as no control, EventHandler as an action excluded from seeded args, and attribute overrides beating inference. Garbage input — scale: "not-a-number" — falls back to the story's typed default instead of panicking, which matters because args arrive from a URL.

P2 is confirmed as a genuine advantage rather than a workaround: the macro sees names, types and docs statically, and the applier it emits is checked by the compiler. One constraint surfaced — rsx! and EventHandler::new need an active Dioxus scope, not merely a runtime, so story bodies are fn pointers invoked inside the preview component rather than eagerly-evaluated functions.

06

Milestone plan

Ordered so each milestone ships something usable on its own. The estimates assume one person working steadily, and they are the least reliable numbers on this page.

  1. M0Feasibility spikescompletedone

    Three go/no-go questions, each a throwaway binary, all answered before any product code is written. One: does dx serve hot-patching survive a registry lookup, and does editing a story file update the running preview while keeping the selection? Two: does a linkme distributed slice survive wasm-opt and section GC in a release build? Three: can a Controls derive read doc comments and produce an applier that type-checks?

    ResultMet, with hot-patching switched off: a story renders, controls edit props live, and a source edit rebuilds in 1.5s. Full results in section 05.

  2. M1Walking skeleton2–3 weeks

    Core types, the #[story] and story_meta! macros, the registry, an in-process Channel, the manager shell with a sidebar tree built from title paths plus search and keyboard navigation, the preview harness, and URL routing by story id.

    ShipsBrowse and render stories. Already useful on its own.

  3. M2Controls & actions3–4 weeks

    The differentiating milestone. derive(Controls) and ControlEnum; ArgValue for primitives, enums, Option<T> and Vec<T>; widgets for text, number, range, bool, select, radio and color; the Controls panel with reset-to-default; args encoded in the URL; EventHandler auto-wiring into an Actions panel; and args write-back so inputs behave.

    ShipsThe wow loop. This is where it stops being a gallery.

  4. M3Isolation, globals & environment2–3 weeks

    Split manager and preview into two wasm bundles behind a postMessage channel — with no addon changes, if P4 was done right. Decorators at three levels, parameters with merge semantics, globals and toolbar, the viewport, backgrounds, measure and outline addons, and an error boundary that reports panics to the manager.

    ShipsRobustness and environment testing. Unblocks everything downstream.

  5. M4Documentation~3 weeks

    An autodocs page per component; a props table built from arg types and doc comments; a source snippet per story, captured by the macro as a static string from the rsx token stream; component descriptions from doc comments; a docs and canvas tab toggle.

    ShipsThe design-system deliverable. Highest external value per unit of work on the whole plan.

  6. M5Static build & publish1–2 weeks

    A static site export, an index manifest, deep-linkable preview URLs carrying story id and args, and a CI recipe for GitHub Pages.

    ShipsA shareable artifact. Pull this forward if adoption matters more than rigour.

  7. M6Testing4–6 weeks

    The testing crate with DOM queries and user events; #[play] execution with an Interactions panel and step log; an accessibility addon loading axe-core in the preview and piping violations back over the channel; a headless runner over the static build covering render tests and play functions; and visual-regression snapshotting with pixel diffs.

    NoteAccessibility is disproportionately cheap — axe-core is a drop-in — and disproportionately valuable. Consider pulling it into M3.

  8. M7Extensibilityongoing

    A public addon trait — manager half, preview half, channel messages — plus presets, UI theming, and story composition across packages.

    DeferredMDX needs a Rust pipeline; use plain Markdown with doc blocks instead. Composition, coverage and design-tool embeds wait too.

07

Open decisions

Five questions that change the plan rather than merely detail it. The first and third are the ones worth settling before M1.

01How far does this go?

A personal component workbench (M0 through M3), or a publishable crate aimed at the design-system market (M0 through M6)? This changes API-stability discipline and documentation burden in every milestone, so it is worth answering first.

02Which registry mechanism?

Settled by the M0 spike, but the fallback appetite is worth agreeing on now: is a build.rs codegen step acceptable, or is magic-free explicit registration preferable to either?

03Publish first, or test first?

Ship M5 early for adoption and stakeholder buy-in, or M6 early for engineering rigour. Both cannot go first, and the answer depends entirely on who this is for.

04Is desktop mode in scope at all?

dx serve --platform desktop is nearly free once the web path works — but "nearly free" has a way of not staying that way. Web-only forever is a defensible answer.

05What is it called?

dx-story, dioxus-storybook, or something else. Matters before the first publish to crates.io, and not after.
