# dioxus-storybook

A native [Storybook](https://storybook.js.org/) for [Dioxus](https://dioxuslabs.com).

Declare each of your component's states as a *story*, render it in isolation,
and browse the lot in a workbench — with the selected story and its arguments
carried in the URL, so a rebuild puts you back exactly where you were.

> **Status: M1, the walking skeleton.** Stories are discovered, indexed,
> browsable and rendered. `#[derive(Controls)]` already builds the props table
> from your types and doc comments; the panel that *edits* those controls is M2.
> **Not published to crates.io yet** — use a git dependency for now.

## What it looks like

One file per component. No configuration, no registration list.

```rust
use dioxus_storybook::prelude::*;
use crate::button::{Button, ButtonProps, ButtonVariant};

story_meta! {
    title: "Forms/Button",     // the sidebar path, split on `/`
    component: Button,
    tags: ["autodocs"],
}

fn base() -> ButtonProps {
    ButtonProps {
        label: "Click me".into(),
        variant: ButtonVariant::Primary,
        scale: 1.0,
        disabled: false,
        tooltip: None,
        onclick: EventHandler::new(|_| {}),
    }
}

#[story]
fn primary() -> ButtonProps {
    base()
}

#[story]
fn danger() -> ButtonProps {
    ButtonProps {
        variant: ButtonVariant::Danger,
        label: "Delete".into(),
        ..base()
    }
}

/// The escape hatch: return `Element` and compose whatever you like.
#[story(name = "Button Row")]
fn button_row() -> Element {
    rsx! {
        div { style: "display:flex; gap:10px;",
            Button { ..base() }
            Button { variant: ButtonVariant::Ghost, label: "Learn more".into(), ..base() }
        }
    }
}
```

Controls and the props table come from the props type itself — field names,
types and `///` comments:

```rust
#[derive(Props, Clone, PartialEq, Controls)]
pub struct ButtonProps {
    /// Text shown inside the button.
    pub label: String,
    /// Visual emphasis of the button.
    pub variant: ButtonVariant,          // enum -> select, via #[derive(ControlEnum)]
    /// Relative size multiplier.
    #[control(range(min = 0.75, max = 2.5, step = 0.05))]
    pub scale: f32,
    /// Optional tooltip shown on hover.
    pub tooltip: Option<String>,         // Option<T> -> optional
    /// Fired on click.
    pub onclick: EventHandler<MouseEvent>,   // handler -> actions, never a widget
}
```

## Quick start

```toml
[dependencies]
dioxus = { version = "0.7", features = ["web"] }
dioxus-storybook = { git = "https://github.com/dw3labs/dioxus-storybook" }

[build-dependencies]
dioxus-storybook-build = { git = "https://github.com/dw3labs/dioxus-storybook" }
```

`build.rs` — finds your stories at build time:

```rust
fn main() {
    dioxus_storybook_build::index("src/stories").unwrap();
}
```

`src/main.rs`:

```rust
use dioxus::prelude::*;
use dioxus_storybook::prelude::*;

mod button;
mod stories {
    include!(concat!(env!("OUT_DIR"), "/dioxus_storybook_registry.rs"));
}

fn main() {
    dioxus::launch(|| rsx! { Storybook { registry: stories::registry() } });
}
```

```console
$ dx serve --platform web
```

Dropping a new file into `src/stories/` is enough — the generated registry
declares the modules too, so there is no `mod.rs` to keep in sync.

A complete working project lives in [`examples/button-gallery`](examples/button-gallery).

## Design decisions worth knowing

Four of these were settled by writing throwaway binaries and measuring, and two
of the measurements contradicted confident prior assumptions. The full write-ups
are in [`log/`](log).

**The registry is generated by a build script**, not a link-section trick.
`linkme` does not compile for `wasm32` at all, and `inventory` compiles but
*silently drops* any story in an unreferenced codegen unit — passing at
`codegen-units = 1` and failing at 16 and 256. Release uses one unit and dev
uses 256, so stories would vanish while you develop and reappear in production.
Codegen emits explicit `&'static` references that no linker decision can drop.

**Stories are `fn` pointers, not values.** `rsx!` and `EventHandler::new` need
an active Dioxus *scope*, not merely a runtime, so story bodies are invoked from
inside the preview component.

**Args are overlaid, not deserialised.** Props hold `EventHandler` and
`Element`, which serde cannot touch. `#[derive(Controls)]` emits a
compiler-checked *applier* that lays dynamic values over a typed base, keeping
the story's own defaults for anything missing or unconvertible — so a malformed
URL lands on the story rather than a panic.

**The URL is load-bearing, not a sharing nicety.** `dx serve --hot-patch` does
not build on wasm, so every source edit reloads the page and destroys every
signal. The query string is what carries the selected story and its args across
a rebuild. Incremental rebuilds measure ~1.5s, which is what the dev loop
actually rests on.

**The manager never calls the preview directly.** It emits events on a
`Channel` the preview subscribes to. Both halves share one bundle today; that
indirection is what lets the preview move into an iframe at M3 without any
component changing.

## Developing

```bash
cargo test --workspace          # 43 tests + 8 doctests
rust-analyzer diagnostics .     # must stay clean — see below
cd examples/button-gallery && dx serve --platform web
```

`rust-analyzer diagnostics` is part of the definition of done here, not a
nicety. An early version of the `story_meta!` bridge compiled, passed every
test and built for wasm — while making rust-analyzer report a false
`E0425: no such value in this scope` on every story, because a value created in
an attribute-macro expansion cannot cross into a proc-macro-generated
`macro_rules!` (compare [rust-analyzer#10644](https://github.com/rust-lang/rust-analyzer/issues/10644),
open since 2021). A green test suite is not evidence that a macro-based
authoring surface is usable in an editor.
